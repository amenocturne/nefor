# Capability Nodes

Besides agents, Nefor's libraries ship deterministic and human capability
nodes: process execution, POSIX shell scripts, Git worktrees, and human
approval gates. Each constructor returns an ordinary `Node<I, O>` that composes
like any other. This chapter is their reference: inputs, outputs, and which
outcomes are routeable data versus run failures.

## Process and shell nodes

Use structured `exec` when one executable plus arguments expresses the
operation:

```mag
import nefor.{ProcessExecParams, Timeout, cwd, exec}

exec("search", ProcessExecParams {
  argv: ["rg", "-n", "TODO", "src/"],
  cwd: cwd,
  timeout: Timeout.Unlimited,
})
```

`argv` is passed directly to process spawn. No shell is inserted, so operators
such as `|`, `>`, glob expansion, and shell built-ins are ordinary arguments.
For shell syntax, use an explicit POSIX `script`, which runs as
`["/bin/sh", "-c", script]`:

```mag
import nefor.{ShellScriptParams, Timeout, script}

script("bounded-search", ShellScriptParams {
  script: strip_margin("""|rg -n 'TODO|FIXME' src/
                            |  | sort"""),
  cwd: ".",
  timeout: Timeout.Seconds(30),
})
```

POSIX shell does not imply Bash. When Bash semantics are required, invoke it
explicitly through `exec`, for example
`argv: ["/bin/bash", "-lc", "set -o pipefail; command"]`.

Both nodes have type `Node<Unit, ProcessResult>`. Their `cwd` is required;
relative paths resolve from the MAG host's inherited working directory, exposed
as `cwd` (`"."`). An unfed node receives one automatic activation, while an
incoming `Unit` edge makes it dependency-driven.

`ProcessResult` contains separate `stdout` and `stderr` plus a nominal
`ProcessExited {code}` or `ProcessSignaled {signal}` termination. Use an
exhaustive `match` to distinguish them, as
[Development Workflows](<04. Development Workflows.md>) does; authored MAG never
compares termination strings. A nonzero exit is result data, not a failure.
Compile success proves only that the node is well-formed, not that its
executable, working directory, or permissions will work.

## Timeouts

Timeouts are mandatory and explicit. A timeout is a `Timeout` value,
constructed through the type. `Timeout.Unlimited` is unbounded; use it only
when waiting indefinitely is intentional, because a process that never exits
keeps its run, and anything awaiting that run, waiting indefinitely.
`Timeout.Milliseconds(n)`, `Timeout.Seconds(n)`, and `Timeout.Minutes(n)` set a
positive wall-clock bound. Zero, negative, and overflowing durations fail compilation
when the node is constructed.

Reaching the bound is not a `ProcessResult`. The process capability reports it
as a failure, as it does a spawn error; the node exposes no output for either,
so the run fails with `mag.run_failed`.

## Worktrees

`create` and `open` are typed `Node<Unit, Worktree>` constructors:

- `create(id, CreateSpec {repository, path, branch, base})` creates a fresh
  branch and worktree. It refuses to adopt an existing path or local branch.
- `open(id, OpenSpec {repository, path, branch})` validates an existing
  repository, path, and branch triple and never creates or changes it.

Both require absolute repository and worktree paths. The resulting `Worktree`
carries `repository`, `path`, `branch`, and `head`; route it into agents that
need the isolated path. Do not retry `create` as `open` unless reuse was an
explicit orchestration decision.

A mismatch or Git failure is not routeable from MAG: the nodes expose only the
`Worktree` output, so the run fails with `mag.run_failed`. A successful
worktree outlives the run. Run completion is not a merge or cleanup, and the
library intentionally has no merge, removal, inventory, or cleanup node; keep
integration and cleanup outside the graph.

## Human approval gates

`approval_gate(id, ApprovalConfig {prompt})` has type
`Node<TextAnswer, HumanWorkflowDecision>`. The decision is
`Approved(HumanWorkflowApproval {content})` or
`Rejected(HumanWorkflowRejection {reason})`; route both constructors. Use it
when a human decision is part of the workflow's meaning. It is separate from
tool-invocation approval (`ToolApprovalPolicy`) and from the lead workflow's
plan review. The runtime side of the request and reply is the
[approval boundary](../../../plugins/mag/docs/actor-model.md#the-approval-boundary).
