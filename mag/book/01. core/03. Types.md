# Types

MAG checks every program before producing its artifact. Function parameters,
returns, collection items, record fields, and artifact data all participate in
the same type system.

## Nominal records

`type` gives a name to a shape:

```mag
type Score {name: String, accepted: Bool}
```

Named types are nominal. A record constructor names its owner explicitly:

```mag
Score {name: "example", accepted: true}
```

Records are closed: every declared field is required and extra fields are
rejected. Braced fields belong to a named constructor; they do not create an
independent anonymous record merely because their fields have the same shape.

## Algebraic data types and tuples

A nominal algebraic data type describes one of several alternatives:

```mag
type Accepted {score: Score}
type Rejected {score: Score, reason: String}
type Decision = Accepted(Accepted) | Rejected(Rejected)
```

An anonymous product is an ordered tuple. Order, arity, repetition, and grouping
are preserved:

```mag
(String, Int)
```

ADTs and products are data constructors rather than control flow. A program
constructs a sum case through its owning type:

```mag
let decision: Decision = Decision.Accepted(
  Accepted {score: Score {name: "review", accepted: true}},
)
```

`Type.Constructor(payload)` is the only construction spelling, and it works in
any expression position without a type annotation. The owner is any name that
resolves to the type: a local declaration, an imported or qualified name, or an
alias. A constructor with a `Unit` payload takes no arguments
(`Flag.Off()`), several arguments form a tuple payload, and `name: value`
arguments form an inline record payload. A constructor name used on its own,
such as `Accepted(...)`, is an ordinary function call, not a construction.

Constructors live in the scope of their type, not in the module scope. Two
types in one module may therefore declare the same constructor name, and a
constructor never collides with a function, an import, or a type of the same
name. Within one type, constructor names must be unique.

`match` consumes the sum without duplicating its constructor as a string field:

```mag
let explanation = match decision {
  case Accepted(accepted) => get(get(accepted, "score"), "name"),
  case Rejected(rejected) => get(rejected, "reason"),
}
```

Every arm has the form `case Constructor(binding) => expression`. The binding
has the concrete payload type inside that arm, so `accepted` above is
`Accepted`, not the broader `Decision`. Arms must cover every constructor
exactly once and return one compatible type. The checker rejects a missing,
repeated, or foreign constructor; evaluation selects from constructor evidence
already retained by MAG rather than inspecting serialized data.

A sum can also declare payload records inline:

```mag
type InlineDecision = Accepted(Score) | Rejected {score: Score, reason: String}
```

## Generic types

Types can declare parameters:

```mag
type Box<T> {value: T}
type Entry<K, V> {key: K, value: V}
```

`Box<String>` and `Box<Int>` retain the same reusable shape with different item
types. `Entry<String, Int>` substitutes `String` for `K` and `Int` for `V` in
the same two-parameter shape. Generic functions can quantify over the same
parameters.

Generic sums apply their owner arguments at construction:

```mag
type Option<T> = Some(T) | None(Unit)

let render_option: fn(Option<Int>) -> String = |option| => match option {
  case Some(present) => str(present),
  case None(absent) => "none",
}

let answer: Option<Int> = Option<Int>.Some(42)
```

The type arguments are written explicitly at the construction; they are not
inferred from the payload or from an annotation. Named aliases of
`Option<Int>` preserve the same exhaustive constructors.

The complete [`02-types.mag`](../../examples/02-types.mag) program defines a
local result ADT and returns one selected arm. The
[`03-functions.mag`](../../examples/03-functions.mag) program constructs a
generic `Entry<K, V>`.

## Type evidence

```mag
type Finding {path: String, line: Int}
type EvidenceArtifact {descriptor: TypeDescriptor, identity: SemanticTypeId, schema: TypeSchema}

let tag = type_tag<Finding>()
let descriptor = type_evidence(tag)
artifact(EvidenceArtifact {
  descriptor: descriptor,
  identity: type_id(descriptor),
  schema: type_schema(tag),
})
```

`type_tag<T>()` can only name a type known to the checker. Its runtime value has
static type `TypeTag<Finding>`: it is an opaque checked witness, although it
serializes as the semantic descriptor shown below. `` `type_evidence` ``
projects that witness to a `TypeDescriptor`. `` `type_id` `` converts a
descriptor to a `SemanticTypeId`, serialized as a stable SHA-256 string.
`` `type_schema` `` converts a tag to a versioned `TypeSchema` value suitable
for validating external JSON. Ordinary records cannot forge any of these opaque
runtime values.

The artifact above contains these concrete JSON values:

```json
{
  "descriptor": {
    "kind": "named",
    "name": "main.Finding",
    "arguments": [],
    "body": {
      "kind": "record",
      "fields": [
        { "name": "line", "type": { "kind": "primitive", "name": "Int" } },
        { "name": "path", "type": { "kind": "primitive", "name": "String" } }
      ]
    }
  },
  "identity": "sha256:a2d196eef2c34258fec896f83addbe8280c53d7e681ccd40e0e69425e3db66dc",
  "schema": {
    "version": 2,
    "root": {
      "kind": "named",
      "name": "main.Finding",
      "body": {
        "kind": "record",
        "fields": [
          { "name": "line", "schema": { "kind": "int" } },
          { "name": "path", "schema": { "kind": "string" } }
        ]
      }
    }
  }
}
```

The identity is the stable hash of this semantic descriptor. Qualifying the
type under another module name changes both the descriptor name and its
identity. A tag and descriptor serialize to the same JSON descriptor today,
but their runtime types remain distinct: functions expecting a `TypeTag`
cannot be passed a `TypeDescriptor`, or vice versa.
