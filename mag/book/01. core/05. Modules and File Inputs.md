# Modules and File Inputs

A module identity is its path relative to a configured module root:
`modules/labels.mag` is `modules.labels`. Imports are direct source-block
declarations, not runtime module values. Each module evaluates once per
compilation; circular imports are rejected. Only direct top-level `let` and type
declarations are exports, and a module's final expression is ignored.

## Import visibility

The import spelling states exactly which names become visible:

```mag
// Qualified references only.
import modules.labels.{}
let first = modules.labels.title

// Open every direct export and retain qualified access.
import modules.labels
let second = title

// Open selected exports, optionally renamed.
import modules.labels.{title, number_label as label}

// A static namespace alias opens no exports and does not authorize the
// canonical modules.labels.* spelling.
import modules.labels as labels
let third = labels.title
```

For each module, unqualified visibility is computed as **automatic opens −
suppressions + positive selectors**. The three sets compose independently of
declaration order. A selector renamed to `_` subtracts only the spelling that a
bare import would open automatically:

```mag
import modules.labels
import modules.labels.{title as _}

// number_label is open; title remains available as modules.labels.title.
```

Suppression therefore keeps qualified access and cannot override an explicit
positive selector for the same export. Repeated imports and selectors compose
as sets. Canonical imports of descendants share a namespace
trie, but namespace roots, aliases, opened names, selected names, builtins, and
direct local declarations may not collide. A collision is an error rather than
a source-order choice. Repair it by using `import m.{}`, selecting fewer names,
renaming a selector or namespace, or suppressing an automatic spelling.

Values follow the same rule as local declarations: one name may denote several
values of different types, and it collides only when two of them have the same
type. Imported values and local `let` bindings of one name therefore form an
overload set, however each import exposes the name:

```mag
import numbers.{render}   // render: fn(Int) -> String
import texts.{render}     // render: fn(String) -> String
let render: fn(Bool) -> String = |flag| => str(flag)

// render(1), render("x") and render(true) each select one overload.
```

A call that matches none or several of the overloads is reported at the call.
Two sources that give one name the same type collide, and the diagnostic names
both, the shared type, and the same repairs as above. Value collisions are
found once the imported modules have been evaluated, because that is when
their types are known; an imported module that fails to evaluate reports its
own error first.

Types are not overloadable, but one type may reach a name by several paths.
Imports that bring the same name for the same type are one binding: a type
imported from its defining module and again through a transparent alias of it
(`type Shape = shapes.Shape` in another module) do not collide. Two different
types under one name do, and the diagnostic names both. A `newtype` is a
distinct type, so it collides with the type it wraps, and an alias that fixes
a type argument is a different type from the generic one. An imported type
and a local declaration of the same name always collide. Constructors live in
the scope of their type and never take part in these collisions.

Visibility is non-transitive. If `a` imports `b`, importing `a` does not permit
`b.name`; the consumer must import `b` directly. Every qualified value or type
reference likewise requires a matching direct canonical import or namespace
alias. The removed `import m.*` form is not syntax.

When an unqualified value or type is unresolved, the compiler may list sorted
imports whose files statically declare that direct export. This diagnostic
index parses candidate files but never evaluates them, follows their imports,
or reads their file inputs. A suggestion remains advisory; it never changes
name resolution.

## Transparent aliases and newtypes

Alias-shaped `type` declarations are transparent alternate spellings:

```mag
type Label = String
type Pair<T> = (T, T)
```

After generic substitution, an alias is exactly its target for assignment,
function calls, construction, inference, descriptors, schemas, and semantic
IDs. Record declarations and algebraic data types remain nominal.

Use `newtype` when the same runtime representation needs distinct static and
semantic identity:

```mag
newtype UserId = String

let raw = "u-1"
let id: UserId = (raw: UserId) // explicit introduction
let text: String = (id: String) // explicit elimination
```

A declaration annotation does not cross the boundary: `let id: UserId = raw`
is rejected. Expression ascription may cross one boundary between a newtype and
its fully substituted target. Unrelated newtypes require elimination to their
shared representation followed by a separate introduction. Newtype evidence
retains the qualified nominal owner; transparent aliases disappear from it.

## Files are immutable compilation inputs

`read` captures raw text and `read_json` parses JSON:

```mag
let prompt = read("data/prompt.md")
let manifest = read_json("data/manifest.json")
let project_name = get(manifest, "project")
```

The first evaluated read of a resolved path adds its contents to the immutable
compilation snapshot; later reads reuse it. Diagnostic module indexing does not
observe or evaluate these inputs.
